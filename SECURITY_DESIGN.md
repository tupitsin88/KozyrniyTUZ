# Проектные решения безопасности

Документ фиксирует решения S04 для [модели угроз](THREAT_MODEL.md) и [требований безопасности](SECURITY_REQUIREMENTS.md). Решения относятся к планируемой архитектуре Go API, TypeScript-клиента и PostgreSQL. Перечисленные проверки являются планом для последующей реализации, а не отчётом о выполненных тестах.

Основные цепочки трассировки:

| Угроза | Требование | Решение |
| --- | --- | --- |
| `T-01` — чтение материалов чужого клуба | `SR-01` | `D-02` |
| `T-03` — архивирование с подменённым полномочием | `SR-03`, `SR-09` | `D-01`, `D-02` |
| `T-04` — действие старых прав после архивирования | `SR-01`, `SR-03`–`SR-06` | `D-02`, `D-03` |
| `T-05` — решение по заявке чужого клуба | `SR-04` | `D-02`, `D-03` |
| `T-06` — изменение членства чужого клуба | `SR-05` | `D-02`, `D-03` |
| `T-07` — создание или изменение материала без полномочия | `SR-06` | `D-02`, `D-03` |
| `T-11` — восстановление паролей из хранилища | `SR-10` | `D-04` |

## D-01 — Серверная сессия и авторитетный действующий субъект

Версия решения: `v2`, S04.

### Контекст и проблема

Все решения о доступе зависят от того, кем Go API считает отправителя. Браузер пересекает `TB-01` и может прислать чужой `user_id`, заявить иную роль либо повторить старый контекст входа. Если сервер доверяет этим сведениям, обычный User сможет выдать себя за SuperUser и реализовать `T-03` вопреки `SR-09` и `SR-03`.

### Связи

- основная цепочка: `T-03 → SR-09 → D-01`; право архивировать клуб дополнительно проверяет `D-02` по `SR-03`;
- точки входа: `EP-01` и все защищённые обращения к Go API;
- CSRF-контроль ниже является защитой в глубину для браузерной сессии, а не отдельной зафиксированной угрозой.

### Решение и защитные меры

- TypeScript-клиент и Go API работают в одном origin: для локальной первой версии Go-сервер раздаёт оба по `http://localhost:8080`, а в production оба компонента публикует один reverse proxy. Доверенный origin задаётся точным сочетанием схемы, имени хоста и порта.
- После успешной проверки учётных данных сервер создаёт новый непрозрачный токен не менее чем из 32 случайных байт. Значение существующей до входа cookie не переиспользуется; если этот браузер уже прислал действительную сессию, её запись отзывается при замене. Сессии других браузеров не затрагиваются.
- В PostgreSQL хранится только SHA-256-отпечаток токена с полями `user_id`, `created_at`, `last_seen_at`, абсолютным `expires_at` и `revoked_at`. Исходный токен не попадает в базу, URL или журналы.
- В production токен передаётся cookie `__Host-session` с атрибутами `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` и без `Domain`. Для локального HTTP допускается отдельное host-only имя cookie без `Secure`; production-имя и ослабленные параметры там не имитируются.
- Сервер применяет конечные настраиваемые idle- и absolute-timeout. Они проверяются по серверной записи на каждом защищённом запросе; `Max-Age` cookie не является источником истины. Разрешённая активность обновляет `last_seen_at`, но не продлевает абсолютный срок.
- Запись сессии содержит ссылку только на пользователя. Глобальная роль, право Administrator и членство читаются из актуального состояния при каждом запросе, поэтому изменение полномочий действует сразу.
- Первый logout требует точный доверенный `Origin`, действующую сессию и её CSRF-токен; затем сервер помечает текущую сессию отозванной и очищает cookie с теми же именем, `Path` и областью хоста. Повторный logout с уже отсутствующей или отозванной сессией при точном доверенном `Origin` только повторно очищает cookie и возвращает `204`, не признавая старый токен действительным и не выполняя других операций. Другие сессии пользователя не отзываются без отдельной функции.
- Вместе с каждой сессией создаётся отдельный случайный synchronizer CSRF-токен. Он хранится на сервере вместе с сессией, возвращается в JSON успешного входа и может быть повторно получен после перезагрузки через безопасный same-origin endpoint текущей сессии с `Cache-Control: no-store`. Токен не передаётся в cookie, URL или журналы.
- Каждый изменяющий запрос требует одновременно точного доверенного `Origin` и заголовка `X-CSRF-Token`, совпадающего с текущей сессией. Отсутствующий либо равный `null` Origin отклоняется. Токен другой, прежней или отозванной сессии не подходит. С новой сессией создаётся новый CSRF-токен.
- Регистрация и вход, для которых сессионного CSRF-токена ещё нет, принимают только JSON и только с точным доверенным `Origin`; cross-origin запросы отклоняются. Изменение состояния методом `GET` запрещено.
- На каждом защищённом запросе Go API проверяет отпечаток, отзыв и оба срока, после чего устанавливает субъекта исключительно по серверной записи. Клиентские `actor_id`, `current_user_id`, `user_id` отправителя и роль игнорируются либо приводят к ошибке. `target_user_id` допустим только как объект разрешённой административной операции.
- Отсутствующая, поддельная, истёкшая или отозванная сессия приводит к отказу по умолчанию без защищённых данных и изменения состояния.

### Обоснование

Серверная непрозрачная сессия позволяет немедленно отозвать контекст входа и применять актуальные роли без доверия к клиенту. Новый токен после входа предотвращает фиксацию заранее известного идентификатора сессии. Серверные сроки и отзыв сохраняют контроль после выдачи cookie, а synchronizer-токен и точная проверка origin ограничивают межсайтовые изменяющие запросы.

### Существенная альтернатива

Самодостаточный подписанный JWT с `user_id` и ролью уменьшил бы число обращений к хранилищу. Для первой версии он отклонён: немедленный отзыв и применение изменившейся роли сложнее. Решение можно пересмотреть при нескольких независимых API или внешнем поставщике идентификации, если появится обоснованная потребность в stateless-аутентификации.

### Предположения

- генераторы токенов используют криптографически стойкий источник случайности;
- таблица сессий недоступна пользователям напрямую;
- часы сервера достаточно точны для проверки сроков;
- PostgreSQL доступен при защищённом запросе;
- production-развёртывание использует TLS и один явно заданный origin.

### Ограничения

- решение не предотвращает компрометацию устройства или кражу уже действующей cookie вместе с CSRF-токеном;
- оно устанавливает субъекта, но права на конкретный объект проверяет `D-02`;
- межсайтовый клиент потребует отдельного пересмотра origin, CORS и способа аутентификации;
- проверку и хранение пароля определяет `D-04`.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| До входа браузеру задан известный идентификатор cookie | Выполнить успешный вход | Выдан новый токен; предзаданный токен не становится действительной сессией |
| Один браузер повторно входит при действующей сессии, а другой браузер имеет отдельную сессию того же пользователя | Сравнить токены и повторить запрос со старым токеном первого браузера | Новый токен содержит не менее 32 случайных байт и отличается от обоих старых; заменённый токен отклонён, сессия второго браузера действует |
| Успешный вход | Проверить БД, ответ и журналы | В cookie есть новый raw-токен, в БД — только его отпечаток и сроки; raw-токена нет в URL и журналах |
| Страница перезагружена при действующей сессии | Запросить endpoint текущей сессии | Возвращён CSRF-токен этой сессии с `Cache-Control: no-store` |
| Есть две действующие сессии одного пользователя | Отправить запрос второй сессии с CSRF-токеном первой | Отказ; состояние не изменяется |
| Действительная сессия, но токен отсутствует либо `Origin` отсутствует, равен `null` или отличается схемой, хостом либо портом | Выполнить изменяющий запрос | Отказ; состояние не изменяется |
| Нет сессии | Отправить cross-origin регистрацию или вход либо запрос не с JSON | Отказ; учётная запись и сессия не создаются |
| Нет действительной сессии | Запросить защищённое чтение, затем защищённое изменение | Оба запроса отклонены; защищённые данные не возвращаются и состояние не меняется |
| Действительная сессия User | Передать чужой ID отправителя и роль SuperUser при архивировании | Субъектом остаётся владелец сессии; операция отклонена, клуб активен |
| Действительная сессия User | Открыть собственный профиль | Профиль определяется субъектом из сессии и возвращается без клиентского actor ID |
| Роль пользователя изменена после входа | Повторить защищённое действие в той же сессии | Немедленно применяются новые полномочия, а не роль времени входа |
| Хранилище сессий недоступно | Обратиться к защищённой операции | Безопасный отказ без использования закэшированной роли и без изменения состояния |
| Выполнен logout | Повторить logout, затем предъявить старый токен | Logout остаётся успешным и безопасным; старый токен не принимается |
| Превышен idle- или absolute-timeout при ещё имеющейся cookie | Обратиться к защищённой операции | Отказ; данные не возвращаются, состояние не меняется |

### Внешние основания

- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html);
- [OWASP Cross-Site Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## D-02 — Полное серверное посредничество, объектная авторизация и безопасный вывод

Версия решения: `v3`, S04.

### Контекст и проблема

ID объектов, параметры списков, команды и пользовательские тексты приходят через недоверенную границу `TB-01`. Факт входа, прежнее право архивного клуба или Administrator в одном клубе не дают права на объект другого клуба. Проверка только интерфейса, общей роли или присланного `club_id` оставляет пути для `T-01`, `T-03`–`T-07`. Интерпретация сохранённого текста как HTML или кода дополнительно позволила бы выполнить сценарий в браузере другого пользователя, поэтому первая версия ограничивает формат обычным текстом.

### Связи

- основные цепочки: `T-01 → SR-01`, `T-03 → SR-03/SR-09`, `T-04 → SR-01/SR-03/SR-04/SR-05/SR-06`, `T-05 → SR-04`, `T-06 → SR-05`, `T-07 → SR-06`;
- дополнительное покрытие: `T-02 → SR-02`;
- правило безопасного текстового вывода ниже является защитой в глубину на принятой границе форматов и не образует новую цепочку `T → SR`;
- субъект поступает только из `D-01`, согласованность изменений обеспечивает `D-03`.

### Решение и защитные меры

Каждый защищённый обработчик Go API до чтения или изменения вызывает общий серверный слой авторизации для тройки «субъект — действие — сохранённый объект». Отсутствие объявленной политики означает отказ.

Слой авторизации:

- для существующего объекта загружает его из PostgreSQL и выводит фактический `club_id` из сохранённой связи, а не из дополнительного параметра клиента;
- для нового материала или членства берёт целевой клуб из параметра маршрута, загружает его, проверяет активность и Administrator именно этого клуба и сам записывает проверенный `club_id`; поля `id` и `club_id` в теле создания запрещены и приводят к отказу всего запроса;
- считает `id` и `club_id` материала неизменяемыми; endpoint обновления принимает по allowlist только разрешённые поля содержимого;
- считает пару `user_id + club_id` членства неизменяемой: перенос записи в другой клуб или другому пользователю через update отсутствует; изменение выполняется удалением или созданием отдельно авторизованной пары;
- проверяет состояние клуба и актуальную связь полномочия при каждом обращении, включая прямой запрос по ID;
- при отсутствии объекта, связи или однозначного решения, а также при ошибке чтения полномочий отказывает по умолчанию.

Политики отдельных объектов:

| Действие | Условие разрешения |
| --- | --- |
| Создать клуб | `global_role = User`; наличие Administrator другого клуба не отменяет это базовое действие; владельца и начальные связи задаёт `D-03` |
| Создать заявку | `global_role = User`; наличие Administrator другого клуба не отменяет это базовое действие; клуб активен, членство и pending-инвариант проверяет `D-03` |
| Читать материал | Клуб сохранённого материала активен; у субъекта есть `club-member` этого клуба |
| Читать заявку | Субъект — её владелец либо Administrator активного клуба сохранённой заявки |
| Архивировать клуб | Субъект имеет актуальную глобальную роль SuperUser; клуб активен |
| Рассматривать заявку | `global_role = User` и действующий Administrator активного клуба сохранённой заявки; переход проверяет `D-03` |
| Добавлять или удалять членство | `global_role = User` и действующий Administrator активного целевого клуба |
| Создавать материал | `global_role = User` и действующий Administrator выбранного активного клуба; связь записывает сервер |
| Изменять материал | `global_role = User` и действующий Administrator активного клуба сохранённого материала |

В первой версии глобальные роли User и SuperUser взаимоисключающи, а Administrator является дополнительной связью только для User. Если из-за некорректных данных у SuperUser обнаружена связь Administrator, операции с заявками, членством и материалами отклоняются безопасно; доступной остаётся только отдельно авторизуемая функция архивирования. Так глобальная роль не превращается в неявное клубное право и явно выполняются запреты `SR-04`–`SR-06`.

Политики коллекций и `EP-08` применяются в SQL до пагинации, `count` и любой агрегации:

- публичный список содержит только активные клубы и allowlist полей `id`, `name` и `description`;
- собственный профиль определяется субъектом из `D-01` и содержит только его активные членства;
- список материалов фильтруется сервером по выбранному активному клубу и членству текущего субъекта в нём;
- список заявок доступен владельцу только для его заявок либо Administrator только для заявок его активного клуба;
- владелец продолжает видеть собственную заявку после архивирования клуба согласно `SR-02`, но прежний Administrator архивного клуба больше не получает административную коллекцию и не может её рассматривать.

`club.name`, `club.description`, `application.text` и `material.content` являются недоверенными строками и во всех представлениях выводятся только как текст:

- HTML и Markdown в первой версии не поддерживаются; сервер возвращает строки в JSON с `Content-Type: application/json` и `X-Content-Type-Options: nosniff`;
- TypeScript-клиент использует текстовые узлы, `textContent` либо штатное auto-escaping шаблонизатора;
- для этих полей запрещены `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `dangerouslySetInnerHTML`, исполнение через `eval` и помещение в динамический JavaScript, CSS или URL-контекст;
- сохранённая строка не декодируется повторно в разметку после безопасного вывода.

### Обоснование

Полное посредничество и вывод принадлежности из сохранённого объекта закрывают прямые обращения по ID и несовпадающие пары ID. Неизменяемые связи не позволяют превратить законно доступный объект в объект другого клуба. Фильтрация коллекции до подсчёта не раскрывает существование чужих данных через элементы, количество или страницы. Текстовые DOM-sink не дают браузеру интерпретировать сохранённый ввод как элемент, обработчик события или сценарий.

### Существенная альтернатива

PostgreSQL Row-Level Security могла бы принуждать часть правил в базе. Для первой версии вариант отклонён: единственный Go API остаётся пользовательским путём к данным, а безопасная передача контекста и различающиеся правила чтения и изменения усложнят небольшое приложение. Выбор надо пересмотреть при втором сервисе, служебных выгрузках или прямом доступе к базе.

Проверки только в TypeScript-клиенте обходятся прямым запросом. Разрозненные проверки в обработчиках создают расхождения между одиночными объектами и коллекциями, поэтому также не выбраны.

Разрешение rich text с HTML-sanitizer дало бы форматирование, но добавило бы отдельный язык разметки, зависимость и правила безопасных контекстов. Для первой версии вариант отклонён как не входящий в продукт. При появлении HTML, Markdown или нового потребителя строк команда сначала пересматривает модель угроз и выбирает контекстное кодирование либо поддерживаемый sanitizer.

### Предположения

- Go API — единственный пользовательский путь к PostgreSQL;
- связи Administrator, `club-member`, принадлежность объектов и состояние клуба актуальны;
- защищённые маршруты и политики поддерживаются в едином реестре с отказом по умолчанию;
- `D-01` корректно установил субъекта.

### Ограничения

- решение не предотвращает злоупотребление законным полномочием;
- оно не защищает от компрометации действительной сессии;
- согласованность нескольких записей и гонок с архивированием обеспечивает `D-03`;
- кэш полномочий, второй API или служебный путь потребуют повторного обзора полного посредничества;
- правило текстового вывода не защищает новый клиент или экспорт, который позднее начнёт интерпретировать эти строки как разметку; такой потребитель требует отдельного обзора.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |

## D-03 — Серверные поля, инварианты и атомарные переходы

Версия решения: `v3`, S04.

### Контекст и проблема

Создание клуба, заявки и решение по заявке меняют несколько связанных записей. Подмена владельца, два одновременных решения, две pending-заявки одной пары, гонка управления с архивированием или сбой между статусом и членством могут создать неверное либо частичное состояние.

### Связи

- основные цепочки: `T-05 → SR-04` и `T-04 → SR-03/SR-04/SR-05/SR-06`;
- дополнительное покрытие: `T-06 → SR-05`, `T-07 → SR-06`, `T-08 → SR-07`, `T-09 → SR-08`;
- использует субъекта из `D-01` и политики объектов из `D-02`.

### Решение и защитные меры

Сервер владеет защищёнными полями:

- при создании клуба сам создаёт ID, берёт создателя из `D-01`, задаёт состояние `active` и в одной транзакции записывает клуб, право Administrator и `club-member` создателя; клиент передаёт только название и описание;
- при создании заявки сам задаёт `user_id`, статус `pending` и `created_at`; клиент передаёт только выбранный клуб и текст;
- `user_id` и `club_id` заявки после создания неизменяемы, а статус меняется только допустимым переходом решения;
- при решении пользователь и клуб членства берутся из сохранённой заявки; сервер сохраняет точный `administrator_id` субъекта и время решения.

Предметный инвариант первой версии: у пользователя может быть не более одной pending-заявки в один клуб. Если пользователь уже имеет `club-member` этого клуба либо такую pending-заявку, новая заявка отклоняется. Поля `user_id`, `club_id` и `status` обязательны (`NOT NULL`), а инвариант дополнительно принуждается частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX applications_one_pending_per_user_club
    ON applications (user_id, club_id)
    WHERE status = 'pending';
```

Для `club-member` действует уникальность пары `(user_id, club_id)`.

Все изменения состояния существующего клуба, включая заявку, решение, членство, материал и архивирование, выполняются транзакциями PostgreSQL с уровнем `READ COMMITTED` по одному протоколу. Выдачи, отзыва или передачи Administrator после создания клуба в первой версии нет; при появлении такая операция должна войти в этот же протокол и получить отдельную политику доступа.

1. Для существующего объекта определить сохранённый неизменяемый `club_id`; для создаваемого объекта взять ID целевого клуба из проверяемого параметра маршрута.
2. Первой выполнить `SELECT ... FOR UPDATE` строки клуба.
3. Затем, где применимо, блокировать запись Administrator, а после неё целевую заявку, членство или материал. Несколько строк одного типа блокировать по возрастанию ID.
4. После получения блокировок повторно проверить активность клуба, актуальное полномочие, принадлежность объекта, статус и предметные инварианты.
5. Выполнить все связанные записи и удерживать блокировки до `COMMIT`.
6. Отправлять успешный HTTP-ответ только после однозначно подтверждённого драйвером `COMMIT`. Отсутствие подтверждения не означает `ROLLBACK`; доставка HTTP-ответа не является частью транзакции БД.

Архивирование начинает с той же блокировки клуба. Поэтому если оно получает её первым, последующая управляющая операция видит архив и отказывается; если изменение получило блокировку первым, архивирование ждёт его завершения, а затем архивирует уже согласованное состояние. Транзакция архивирования меняет только состояние клуба на `archived` и серверное время `archived_at`; связанные заявки, материалы, членства и права Administrator сохраняются без изменения, но `D-02` перестаёт считать их действующими.

Рассмотрение pending-заявки переводит её ровно один раз в `approved` или `rejected`. При `approved` статус, `administrator_id`, время и членство фиксируются одной транзакцией; уже существующая законная запись членства сохраняется без удаления, замены или дубликата. При `rejected` новое членство не создаётся, а существующее не изменяется. Подтверждённая ошибка до `COMMIT` откатывает всю попытку; неопределённый результат `COMMIT` обрабатывается отдельно.

Результат каждой попытки классифицируется как подтверждённый `COMMIT`, подтверждённый abort/`ROLLBACK` либо неопределённый исход. `SQLSTATE 40P01` означает, что PostgreSQL прервал текущую транзакцию. После подтверждённого abort допускается малое ограниченное число повторов с jitter: каждый повтор начинает новую транзакцию и заново выполняет чтения, авторизацию, блокировки и проверки; повторять только последний SQL-запрос нельзя. Полный повтор допустим, если все эффекты попытки находились внутри транзакции и подтверждено, что она не была зафиксирована.

Если соединение или протокол завершается ошибкой во время ожидания результата `COMMIT`, PostgreSQL мог уже зафиксировать изменения. Последующий `ROLLBACK` или новое соединение не доказывают обратного. Сервер не сообщает, что состояние осталось исходным, и не повторяет неидемпотентную команду автоматически. Без сохранённого idempotency key с однозначным результатом API возвращает `500` с машинным кодом `transaction_outcome_unknown`; потребитель сначала читает авторитетное состояние. После исчерпания повторов `40P01` ответ `503 Service Unavailable` и гарантия исходного состояния допустимы только при подтверждённом abort каждой попытки.

### Обоснование

Серверное владение полями исключает выбор владельца, начального статуса и получателя членства клиентом. Единый порядок блокировок превращает архивирование и управление в последовательный результат, а транзакция не оставляет состояния «approved без членства». Частичный уникальный индекс сохраняет инвариант pending даже при ошибке прикладной проверки.

### Существенная альтернатива

Уровень `SERIALIZABLE` позволил бы выражать проверки декларативнее, но потребовал бы обязательного корректного повтора всей транзакции при SQLSTATE `40001` и не отменял бы необходимость атомарности. Для небольшой первой версии выбран явный протокол `READ COMMITTED + SELECT ... FOR UPDATE`, потому что общий объект конкуренции — строка клуба — известен заранее.

Выбор пересматривается при операциях без единственной заранее известной строки клуба как общего объекта блокировки, межклубных атомарных изменениях, втором писателе, который не может гарантированно соблюдать протокол, либо измеренном нарушении SLO из-за конкуренции за lock клуба. Высокая конкуренция сама по себе не доказывает преимущество `SERIALIZABLE`: он может увеличить число abort. Переход потребует полного повтора транзакции при `40001` и также не устранит неопределённый исход `COMMIT`.

Последовательные отдельные записи с компенсацией отклонены: между шагами возникает наблюдаемое противоречие, а падение процесса может не дать выполнить компенсацию.

### Предположения

- PostgreSQL обеспечивает транзакции, блокировки строк и уникальные ограничения;
- Go API — единственный писатель прикладных данных;
- связь заявки и материала с клубом неизменяема;
- допустимые статусы ограничены схемой базы;
- все обработчики изменений соблюдают один порядок блокировок.

### Ограничения

- решение не предотвращает ошибочное, но формально разрешённое решение администратора;
- оно не ограничивает общее число заявок в разные клубы;
- история изменений, кроме `administrator_id` и времени решения, пока не предусмотрена;
- повтор транзакции требует аккуратной классификации ошибок и идемпотентности запроса;
- общий lock строки клуба последовательно выполняет изменения одного клуба и может стать ограничением пропускной способности;
- без idempotency key потеря подтверждения `COMMIT` сервером либо потеря HTTP-ответа клиентом может потребовать ручного сопоставления созданного объекта с авторитетным состоянием.

| Операция создания заявки, решения, материала или членства получила блокировку клуба первой | Запустить архивирование | Архивирование ждёт commit операции, затем успешно архивирует согласованное состояние |
| Архивирование получило блокировку клуба первым, а создание заявки ожидает | Зафиксировать архивирование и продолжить создание | Создание видит архивное состояние и получает отказ; заявка не появляется |
| До операции сохранён снимок клуба, заявок, материалов, членств и прав Administrator | SuperUser архивирует активный клуб | Точная дельта: меняются только `status=archived` и `archived_at` клуба; все связанные строки сохранены с прежними значениями, но последующие политики считают их неактивными |
| Искусственный сбой установлен между статусом `approved` и членством | Выполнить решение | Вся транзакция откатывается: остаётся `pending`, `administrator_id` и время не записаны, нового членства нет |
| Искусственный сбой установлен после вставки клуба, но до Administrator и членства создателя | Создать клуб | Вся транзакция откатывается; ни клуб, ни право, ни членство не сохраняются |
| Тестовый слой БД один раз возвращает `SQLSTATE 40P01` до commit; abort этой попытки подтверждён | Выполнить операцию | Новая транзакция повторяет весь протокол и фиксирует операцию один раз; дубликатов и ложного промежуточного успеха нет |
| Тестовый слой БД возвращает `SQLSTATE 40P01` на каждой попытке до лимита; каждый abort подтверждён | Выполнить операцию | После исчерпания лимита API возвращает `503 Service Unavailable`; исходное состояние сохранено, успех не сообщается |
| PostgreSQL фиксирует `COMMIT` создания клуба, но тестовый слой теряет подтверждение до его получения драйвером | Получить `transaction_outcome_unknown`, затем через новое соединение прочитать состояние | Автоматического повтора и обещания rollback нет; чтение показывает точную committed-дельту: один клуб, одно полномочие Administrator и одно членство, без дублей |

### Внешнее основание

- [Документация PostgreSQL о явных блокировках](https://www.postgresql.org/docs/current/explicit-locking.html);
- [PostgreSQL `pg_xact_status` и неопределённый исход при разрыве во время `COMMIT`](https://www.postgresql.org/docs/current/functions-info.html#FUNCTIONS-PG-SNAPSHOT).

## D-04 — Стойкое хранение и проверка паролей

Версия решения: `v1`, S04.

### Контекст и проблема

Регистрация и вход входят в `EP-01`, но одна серверная сессия не определяет, как защищать пароль до её создания. Открытый, обратимо зашифрованный или быстро хешированный пароль в базе либо журнале позволяет реализовать `T-11` и затем войти с полномочиями жертвы.

### Связи

- цепочка: `T-11 → SR-10 → D-04`;
- успешная проверка передаёт управление созданию новой сессии по `D-01`.

### Решение и защитные меры

- Для локальной парольной аутентификации сервер хранит только закодированный проверочный результат Argon2id. Каждая запись содержит версию формата, алгоритм, параметры, уникальную случайную соль и результат; пароль и отдельная обратимо зашифрованная копия не хранятся.
- Абсолютный допустимый минимум первой версии: память 19 MiB, 2 итерации, параллелизм 1. Это же текущая конфигурация по умолчанию (`19 MiB / 2 / 1`); при старте сервер проверяет `minimum ≤ current ≤ maximum` и прекращает запуск при недопустимой конфигурации. Целевые значения можно повысить после измерения задержки и ресурсов.
- Перед вычислением сервер проверяет параметры записи и ограничивает их максимумами первой версии: память 64 MiB, 4 итерации и параллелизм 4. Значения вне диапазона отклоняются, чтобы повреждённая запись не вызвала неконтролируемое потребление ресурсов.
- Соль создаётся криптографически стойким генератором отдельно для каждого пароля, поэтому одинаковые пароли дают разные записи.
- Проверка рассчитанного и сохранённого результатов выполняется сравнением с постоянным временем. Повреждённый формат, неподдерживаемые алгоритм или версия и параметры ниже абсолютного минимума либо выше безопасного максимума обрабатываются безопасно и не создают сессию.
- Ошибка входа одинакова для неизвестного пользователя и неверного пароля; сессия при ошибке не создаётся.
- Сервер не переносит открытый пароль из обработки регистрации или входа в долговременное состояние: не записывает его в БД, ответы, метрики, трассировки, журналы или данные сессии. Поля пароля скрываются структурированным логированием; обработчики не удерживают ссылку на пароль после запроса и избегают лишних копий.
- После успешного входа запись с параметрами внутри допустимого диапазона, но ниже текущих целевых, пересчитывается с целевыми параметрами и новой солью, затем атомарно заменяется.
- Если позднее будет выбран внешний IdP, передача и хранение локальных паролей исключаются из границы; до фактического перехода это не считается реализованной защитой.

### Обоснование

Argon2id с уникальной солью повышает стоимость офлайн-перебора после раскрытия базы и не требует возможности восстановить пароль. Версионированный формат и rehash после успешного входа дают путь обновления параметров без массового знания открытых паролей.

### Существенная альтернатива

Внешний поставщик идентификации избавил бы сервис от локальной обработки паролей, но добавил бы внешний компонент, которого нет в текущей границе и локальном запуске. Альтернативу следует пересмотреть, если такой компонент действительно появится. Быстрые хеши, собственное шифрование и обратимое хранение неприемлемы.

### Предположения

- вход первой версии действительно использует пароль;
- библиотека Argon2id поддерживается и получает случайность от ОС;
- доступ к конфигурации параметров и базе ограничен сервером.

### Ограничения

- решение не делает слабый пароль сильным и не предотвращает повторное использование пароля на другом сайте;
- оно не ограничивает online credential stuffing и не определяет восстановление аккаунта;
- компрометация процесса во время ввода может раскрыть открытый пароль;
- Go и используемые библиотеки могут сохранять копии строк или буферов до сборки мусора либо повторного использования памяти; немедленное стирание всех копий пароля из RAM не гарантируется;
- параметры надо повторно оценить на целевом оборудовании до production.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| Две регистрации используют одинаковый пароль | Сравнить записи в БД | Соли и полные проверочные записи различаются; открытого пароля нет |
| Сервер запущен с текущими параметрами `19 MiB / 2 / 1`, создана новая парольная учётная запись | Разобрать версионированную проверочную запись | Указан Argon2id и ровно текущие параметры `19 MiB / 2 / 1` |
| Есть корректная запись Argon2id | Войти с правильным паролем | Проверка успешна; `D-01` создаёт новую сессию |
| Есть корректная запись Argon2id либо имя пользователя отсутствует | Войти с неправильным паролем или неизвестным именем | В обоих случаях возвращена одинаковая общая ошибка входа; сессия не создана |
| Выполнены регистрация и вход с тестовым секретом | Проверить БД, ответы, обычные и ошибочные журналы | Тестовый секрет нигде не присутствует в открытом виде |
| Запись повреждена либо версия или алгоритм не поддерживаются | Попытаться войти | Безопасный отказ без panic и без сессии |
| Параметры записи ниже абсолютного минимума либо выше максимума | Попытаться войти | Отказ происходит до дорогостоящего вычисления; сессия не создаётся |
| Конфигурация current ниже минимума либо выше максимума | Запустить сервер | Сервер прекращает запуск с контролируемой ошибкой конфигурации |
| Текущие целевые параметры повышены, а запись использует старые параметры внутри допустимого диапазона | Успешно войти | Запись атомарно заменена целевыми параметрами и новой солью |

## Обзор решений и контрпримеры

### Подмена клуба материала

**Ошибочное предположение:** достаточно проверить членство в `club_id`, присланном рядом с `material_id`.

**Контрпример:** член клуба A передаёт разрешённый `club_id=A` и ID материала клуба B. Проверка присланного клуба проходит, хотя объект относится к B.

**Последствие для цепочки:** нарушается `T-01 → SR-01`: участник A получает закрытое содержимое материала B без членства в B.

**Уточнение:** `D-02` загружает материал, получает неизменяемый фактический клуб и проверяет членство именно в нём.

### Конкурирующие решения по заявке

**Ошибочное предположение:** одиночной проверки `status = pending` перед update достаточно.

**Контрпример:** два запроса читают `pending`; один отправляет `approved`, другой `rejected`, либо процесс падает между статусом и членством.

**Последствие:** нарушается `SR-04`: финальный статус и членство могут разойтись — например, `rejected` с членством или `approved` без него.

**Уточнение:** `D-03` использует одну транзакцию, общий порядок блокировок, повторную проверку после блокировки и подтверждённый rollback ошибок до `COMMIT`.

### Две ожидающие заявки

**Ошибочное предположение:** проверки существующей pending-заявки в приложении достаточно.

**Контрпример:** два параллельных запроса одной пары одновременно не видят существующей записи и оба вставляют `pending`.

**Последствие:** сохраняются две pending-заявки пары «пользователь — клуб»; одну можно одобрить, другую отклонить, создав противоречивые результаты рассмотрения.

**Уточнение:** `D-03` закрепляет предметный инвариант частичным уникальным индексом и проверяет его под блокировкой клуба.

### Граница сессионной защиты

`HttpOnly`, exact-origin и CSRF-токен не делают действительную сессию неуязвимой. Если злоумышленник контролирует устройство или получил действующую cookie вместе с токеном, запрос может выглядеть законным. После уточнения модели развёртывания такой сценарий следует оформить новым `T-*`, не переиспользуя исторический `T-10`.
