# Проектные решения безопасности

Документ фиксирует решения S04 для [приоритетных угроз](THREAT_MODEL.md) и связанных [требований безопасности](SECURITY_REQUIREMENTS.md). Решения относятся к планируемой архитектуре Go API и PostgreSQL. Будущие проверки ниже являются планами, а не выполненными тестами или свидетельствами.

Приоритетный набор покрывается следующими цепочками:

| Угроза | Требование | Решение |
| --- | --- | --- |
| `T-01` — чтение материалов чужого клуба | `SR-01` | `D-02` |
| `T-03` — архивирование с подменённым полномочием | `SR-03`, `SR-09` | `D-01`, `D-02` |
| `T-04` — действие старых прав после архивирования | `SR-01`, `SR-03`, `SR-04`, `SR-05`, `SR-06` | `D-02`, `D-03` |
| `T-05` — решение по заявке чужого клуба | `SR-04` | `D-02`, `D-03` |
| `T-06` — изменение членства чужого клуба | `SR-05` | `D-02` |
| `T-07` — изменение материала чужого клуба | `SR-06` | `D-02` |

## D-01 — Серверная сессия и авторитетный действующий субъект

Версия решения: `v1`, S04.

### Контекст и проблема

Все решения о доступе зависят от того, кем Go API считает отправителя запроса. Браузер пересекает `TB-01` и может передать чужой `user_id`, заявить иную роль или обратиться без действительного контекста входа. Если сервер принимает эти сведения как основание полномочий, становится возможным сценарий `T-03`: обычный пользователь заявляет роль SuperUser и архивирует клуб вопреки `SR-09` и `SR-03`.

### Связи

- угроза: `T-03`, в части подмены действующего пользователя или роли;
- основное требование: `SR-09`; разрешение самого архивирования по `SR-03` проверяет `D-02`;
- точки входа: `EP-01` и все защищённые обращения к Go API.

### Решение и защитные меры

- После успешной проверки учётных данных Go API создаёт криптографически случайный непрозрачный токен сессии.
- Сервер хранит в PostgreSQL криптографический отпечаток токена вместе с `user_id`, сроком действия и состоянием отзыва; исходный bearer-токен в базе не сохраняется.
- Браузер получает токен в cookie с `HttpOnly` и `SameSite=Lax`; для развёртывания вне localhost также обязателен `Secure` и защищённое соединение.
- Операции изменения состояния не используют метод `GET`. Для небезопасных HTTP-методов API дополнительно проверяет разрешённый `Origin` и связанный с сессией CSRF-токен из пользовательского заголовка; отсутствие или несовпадение любого из них приводит к отказу.
- На каждом защищённом запросе API проверяет наличие, срок действия и состояние отзыва сессии и устанавливает действующего пользователя только по серверной записи.
- Актуальная глобальная роль и клубные полномочия читаются из авторитетного состояния, а не из полей клиента.
- Клиентские `actor_id`, `current_user_id`, `user_id` отправителя и роль не меняют действующего субъекта. `target_user_id` допускается только как объект разрешённой административной операции.
- Отсутствующая, поддельная, истёкшая или отозванная сессия приводит к отказу по умолчанию без возврата защищённых данных и без изменения состояния.

### Обоснование

Серверная сессия согласуется с небольшим Go-приложением и существующим PostgreSQL. Она позволяет немедленно отзывать контекст входа и применять актуальные роли без доверия к содержимому клиентского запроса. Контроль выполняется сервером и сохраняется при прямом обращении к API.

### Существенная альтернатива

Самодостаточный подписанный JWT с `user_id` и ролью уменьшил бы число обращений к хранилищу сессий. Для первой версии этот вариант отклонён: немедленный отзыв сложнее, а роль внутри токена может устареть после изменения полномочий. Выбор следует пересмотреть при появлении нескольких независимых экземпляров API или внешнего провайдера идентификации, если будет обоснована потребность в stateless-аутентификации.

### Предположения

- токен сессии создаётся криптографически стойким генератором;
- таблица сессий недоступна напрямую пользователям;
- системное время достаточно корректно для проверки срока действия;
- PostgreSQL доступен во время проверки защищённого запроса;
- удалённое развёртывание использует TLS.

### Ограничения

- решение не определяет способ безопасного хранения паролей;
- решение не предотвращает компрометацию устройства или кражу уже действующей cookie;
- решение устанавливает субъекта, но объектные права проверяет `D-02`;
- защита от CSRF рассчитана на браузерный клиент того же origin; появление разрешённых межсайтовых клиентов потребует пересмотра списка origin и способа передачи токена.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| Действительная сессия User | Передать чужой ID отправителя и заявить роль SuperUser при запросе архивирования | Операция выполняется от имени владельца сессии и отклоняется; клуб остаётся активным |
| Сессия отсутствует, поддельна, истекла или отозвана | Обратиться к защищённой операции | Отказ; защищённые данные не возвращаются, состояние не изменяется |
| Действительная сессия Administrator | Указать целевого пользователя в разрешённой операции управления членством | Действующим субъектом остаётся Administrator; целевой ID не становится отправителем |
| Действительная сессия User | Открыть собственный профиль и передать чужой ID отправителя | Возвращается профиль владельца сессии; чужой профиль не возвращается |
| Действительная сессия, но нет корректного CSRF-токена либо указан посторонний `Origin` | Отправить запрос изменения состояния | Отказ; состояние не изменяется |

## D-02 — Полное серверное посредничество и объектная авторизация

Версия решения: `v1`, S04.

### Контекст и проблема

Идентификаторы объектов и команды поступают через недоверенную границу `TB-01`. Факт входа, прежнее право архивного клуба или наличие роли Administrator в одном клубе не дают полномочий на объект другого клуба. Проверка только интерфейса, переданного `club_id` или общей роли оставляет пути для всех шести приоритетных угроз: `T-01`, `T-03`–`T-07`.

### Связи

- основные угрозы и требования: `T-01 → SR-01`, `T-03 → SR-03/SR-09`, `T-04 → SR-01/SR-03/SR-04/SR-05/SR-06`, `T-05 → SR-04`, `T-06 → SR-05`, `T-07 → SR-06`;
- дополнительное покрытие: `T-02 → SR-02`;
- зависит от корректного установления субъекта в `D-01`.

### Решение и защитные меры

Каждый защищённый обработчик Go API вызывает общий серверный слой авторизации для тройки «субъект — действие — объект». Защищённая группа маршрутов не выполняет операцию, пока для неё не объявлена и не прошла политика доступа.

Слой авторизации:

- получает субъекта только из `D-01`;
- для чтения или изменения существующей записи загружает её из PostgreSQL и определяет фактический `club_id` по сохранённой связи;
- для создания материала или членства загружает выбранный целевой клуб как объект авторизации, проверяет его активное состояние и связь Administrator именно с ним, а затем создаёт запись с `club_id`, установленным сервером;
- не использует дополнительно переданный клиентом `club_id` как доказательство принадлежности объекта;
- проверяет активное или архивное состояние клуба;
- при отсутствии объекта, связи или однозначного решения, а также при ошибке получения полномочий, отказывает по умолчанию;
- выполняется при каждом существенном обращении, включая прямой запрос по ID; решение о доступе не кэшируется в первой версии.

Политики первой версии:

| Действие | Условие разрешения |
| --- | --- |
| Читать материал | Клуб активен; у субъекта есть `club-member` именно клуба сохранённого материала |
| Читать заявку | Субъект является владельцем либо Administrator активного клуба сохранённой заявки |
| Архивировать клуб | Субъект имеет актуальную глобальную роль SuperUser; клуб активен |
| Рассматривать заявку | Субъект является Administrator активного клуба сохранённой заявки; допустимый статус дополнительно проверяет `D-03` |
| Менять членство | Субъект является Administrator активного целевого клуба |
| Создавать материал | Субъект является Administrator выбранного активного клуба; сервер связывает новый материал именно с проверенным клубом |
| Изменять материал | Субъект является Administrator активного клуба сохранённого материала |

Роль SuperUser не предоставляет неявных прав на заявки, членство или материалы.

### Обоснование

Решение реализует полное посредничество, минимальные привилегии и безопасный отказ в Go API. Одна схема проверки уменьшает риск различий между интерфейсом и прямым запросом и сохраняет клубную область полномочий для разных типов объектов.

### Существенная альтернатива

PostgreSQL Row-Level Security могла бы принуждать часть правил на уровне базы. Для первой версии этот вариант отклонён: единственный Go API остаётся пользовательским путём к данным, а передача контекста субъекта и разные правила операций заметно усложнят небольшое приложение. Выбор следует пересмотреть при появлении второго сервиса, служебных выгрузок или прямого доступа к базе.

Проверки только в TypeScript-клиенте или разрозненные проверки внутри отдельных обработчиков не являются приемлемой альтернативой: первый вариант обходится прямым запросом, второй создаёт расхождения между путями к одному ресурсу.

### Предположения

- Go API является единственным пользовательским путём к PostgreSQL;
- связи Administrator, `club-member`, принадлежность объектов и состояние клуба в базе актуальны;
- список защищённых маршрутов и их политик поддерживается как единый реестр с отказом по умолчанию;
- `D-01` корректно установил действующего субъекта.

### Ограничения

- решение не предотвращает злоупотребление разрешённым правом внутри законной области;
- решение не защищает от компрометации действительной сессии;
- согласованность операций над несколькими записями обеспечивает `D-03`;
- появление кэша полномочий, второго API или служебного пути потребует повторного обзора полного посредничества.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| User не состоит в клубе либо состоит в другом | Напрямую запросить материал по `material_id` | Отказ без содержимого материала |
| User состоит в активном клубе | Запросить сохранённый материал этого клуба | Материал возвращается |
| User имеет членство в клубе A | Передать `club_id` клуба A и `material_id` клуба B | Отказ; принадлежность выводится из сохранённого материала, а не из присланного `club_id` |
| User или Administrator | Напрямую запросить архивирование активного клуба | Отказ; клуб и связанные записи не изменяются |
| SuperUser | Архивировать активный клуб | Клуб становится архивным, прежние права перестают давать доступ |
| Administrator клуба A | Добавить пользователю `club-member` клуба B | Отказ; новый тег клуба B не создаётся |
| Administrator клуба A, у пользователя есть `club-member` клуба B | Удалить этот тег клуба B | Отказ; существующий тег клуба B сохраняется |
| Administrator активного клуба A | Добавить членство пользователю в клубе A | Создаётся только тег пары «целевой пользователь — клуб A» |
| Administrator клуба A | Рассмотреть заявку клуба B | Отказ; статус, сведения о решении и членство не изменяются |
| Administrator клуба A | Изменить по `material_id` материал клуба B | Отказ; материал клуба B не изменяется |
| Administrator активного клуба B | Изменить сохранённый материал клуба B | Новое содержимое материала сохраняется |
| У пользователя сохранился старый тег архивного клуба | Запросить материал этого клуба | Отказ без содержимого материала |
| У пользователя сохранилось старое право Administrator архивного клуба | Рассмотреть заявку этого клуба | Отказ; заявка и членство не изменяются |
| У пользователя сохранилось старое право Administrator архивного клуба | Изменить членство или материал этого клуба | Отказ; теги и материалы не изменяются |
| SuperUser без членства | Запросить закрытый материал клуба | Отказ без содержимого |
| В реестр защищённых маршрутов добавлен обработчик без политики | Обратиться к новому маршруту | Отказ; данные не возвращаются и состояние не изменяется |

## D-03 — Серверные защищённые поля и атомарные переходы

Версия решения: `v1`, S04.

### Контекст и проблема

Создание клуба, создание заявки и одобрение заявки изменяют несколько связанных данных. Клиентские значения владельца или статуса, повторное решение, два параллельных решения либо сбой между изменением статуса и выдачей тега могут создать неверное или частично сохранённое состояние. `D-02` непосредственно ограничивает `T-05`, а для выполнения полного критерия `SR-04` дополнительно нужны однократный переход и атомарная выдача членства. Операции управления также должны быть согласованы с архивированием клуба, чтобы старое полномочие из `T-04` не сработало в гонке.

### Связи

- основные цепочки: `T-05 → SR-04`; `T-04 → SR-03` и связанные `SR-01/SR-04/SR-05/SR-06` в части согласования с архивированием;
- дополнительное покрытие: `T-08 → SR-07`, `T-09 → SR-08`;
- использует действующего субъекта из `D-01` и объектную авторизацию `D-02`.

### Решение и защитные меры

- При создании клуба API сам создаёт ID клуба и берёт создателя из `D-01`; клуб, право Administrator и `club-member` создаются одной транзакцией. Передача клиентом полей владельца, создателя или начальных прав считается ошибкой и отклоняет запрос целиком.
- При создании заявки API сам задаёт владельца из `D-01`, начальный статус `pending` и время; от клиента принимаются только выбранный активный клуб и текст заявки.
- Попытка передать другого владельца или иной начальный статус отклоняется без создания заявки.
- Все операции изменения, требующие активного клуба, проверяют состояние клуба и выполняют изменение в одной транзакции PostgreSQL. Архивирование клуба использует ту же схему согласования, поэтому конкурирующая управляющая операция либо завершается до архивирования, либо видит архивное состояние и отклоняется.
- Рассмотрение заявки определяет неизменяемый `club_id` из сохранённой заявки, затем в едином порядке блокирует клуб, полномочие Administrator и заявку. После блокировки повторно проверяются активность клуба, полномочие и статус `pending`; только затем допускается переход `pending → approved` или `pending → rejected`.
- Пользователь и клуб для будущего членства берутся из сохранённой заявки, а не из запроса решения.
- При `approved` статус, автор и время решения и тег `club-member` фиксируются вместе; при `rejected` фиксируется решение без выдачи тега. Если нужный тег уже был законно выдан вручную, операция одобрения идемпотентно сохраняет существующий тег и закрывает заявку без создания дубликата.
- На пару `user_id + club_id` для `club-member` действует уникальное ограничение.
- Если заявка уже закрыта или любой шаг завершается ошибкой, транзакция откатывает статус, сведения решения и тег.

### Обоснование

Сервер владеет критичными полями, поэтому клиент не может выбрать владельца, начальный статус или получателя членства. Транзакция и блокировка строки исключают состояние «заявка одобрена, но членство не выдано», дубли тега и два разных результата одной заявки.

### Существенная альтернатива

Последовательное изменение статуса и отдельное добавление тега с компенсацией при ошибке проще на уровне кода, но оставляет наблюдаемое противоречивое состояние между шагами и усложняет обработку конкурирующих запросов. Вариант отклонён. Пересмотр возможен только при переходе на асинхронную архитектуру с надёжным журналом событий и явно принятой eventual consistency.

### Предположения

- PostgreSQL обеспечивает транзакции, блокировку строки и уникальное ограничение;
- других писателей, обходящих Go API, нет;
- связь заявки с пользователем и клубом неизменна после создания;
- статусы ограничены допустимыми значениями.

### Ограничения

- решение не предотвращает ошибочное, но формально разрешённое решение администратора;
- решение не защищает от массового создания заявок;
- решение не задаёт полноценную историю изменений помимо автора и времени решения;
- прямое ручное изменение членства регулируется `D-02` и `SR-05`.

### Будущие проверки

| Исходное условие | Действие | Ожидаемый наблюдаемый результат |
| --- | --- | --- |
| Действительная сессия User | Создать клуб без серверных полей в запросе | Клуб, право Administrator и один `club-member` создаются вместе только для текущего пользователя |
| Создание клуба | Передать чужой `user_id` | Отказ; клуб, права и теги не создаются |
| Действительная сессия User и активный клуб | Создать обычную заявку с текстом | Создаётся одна заявка текущего пользователя со статусом `pending` |
| Создание заявки | Передать чужого владельца или статус `approved` | Отказ; заявка отсутствует |
| Клуб архивирован | Создать заявку | Отказ; заявка отсутствует |
| Заявка имеет статус `pending` | Одобрить её уполномоченным администратором | Статус, автор, время и один тег нужной пары сохраняются вместе |
| Заявка имеет статус `pending` | Отклонить её уполномоченным администратором | Сохраняются статус `rejected`, автор и время решения; новый тег не появляется |
| Заявка уже закрыта | Повторить решение | Отказ; статус, сведения решения и теги не изменяются |
| Два конкурирующих решения | Одновременно отправить `approved` и `rejected` | Успешно только одно; итоговый статус и сведения решения единственны, тег соответствует победившему решению |
| Для владельца pending-заявки уже существует `club-member` её клуба | Одобрить заявку | Заявка становится `approved`; существующий тег сохраняется в единственном экземпляре |
| После начала рассмотрения клуб архивирован либо право Administrator отозвано конкурирующей транзакцией | Продолжить решение | Решение не фиксируется без повторной успешной проверки полномочия и активного клуба внутри транзакции |
| Изменение материала или членства конкурирует с архивированием того же клуба | Выполнить обе операции параллельно | Управляющая операция либо полностью фиксируется до архивирования, либо отклоняется после него; изменение не записывается как действие над уже архивным клубом |
| Искусственный сбой между сменой статуса и выдачей тега | Прервать транзакцию | Сохраняется исходный `pending`, новый тег отсутствует |

## Обзор решений и контрпримеры

### Контрпример к первоначальной авторизации материала

**Исходное предположение:** достаточно проверить членство пользователя в `club_id`, присланном вместе с запросом материала.

**Контрпример:** член клуба A передаёт разрешённый ему `club_id` клуба A и `material_id` закрытого материала клуба B. Проверка присланного клуба проходит, хотя объект относится к другому клубу.

**Последствие:** цепочка `T-01 → SR-01 → D-02` остаётся разорванной, а закрытый материал может быть раскрыт.

**Уточнение решения:** `D-02` сначала загружает материал, получает его фактический клуб из сохранённой связи и проверяет членство именно в нём. В будущую проверку добавлена несовпадающая пара `club_id + material_id`.

### Контрпример к наивной реализации D-03

**Исходное предположение:** проверки `status = pending` перед изменением достаточно.

**Контрпример:** два параллельных запроса из одного или нескольких допустимых сеансов администратора читают `pending`, после чего один отправляет `approved`, а другой — `rejected`; либо процесс падает после сохранения `approved`, но до выдачи членства.

**Последствие:** у одной заявки появляются конкурирующие результаты или несогласованное состояние между заявкой и доступом.

**Уточнение решения:** `D-03` использует одну транзакцию, блокировку строки и откат всех связанных изменений. Будущая проверка включает параллельные решения и искусственный сбой между шагами.

### Граница D-01

`HttpOnly` и серверная проверка не делают действительную сессию неуязвимой. Если злоумышленник получил уже действующую cookie или контролирует устройство пользователя, запрос может выглядеть как запрос законного субъекта. Этот сценарий не входит в актуальную `T-03`: после уточнения модели развёртывания он должен получить новый `T-*` с новым ID и, при необходимости, отдельные требование и решение.
