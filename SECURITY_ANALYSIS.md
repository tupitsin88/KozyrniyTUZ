## Реестр решений

### S09-01 - G115: преобразование длины хеша

- **Место:** [password.go](internal/auth/password.go), `verifyPassword`, преобразование `uint32(len(expected))`.
- **Сигнал:** возможное переполнение `int → uint32`, HIGH / MEDIUM confidence.
- **Проверка причины:** непосредственно перед преобразованием декодированная длина обязана равняться `passwordHashLength`, то есть 32. При другой длине функция возвращает ошибку до Argon2id. Значение 32 представимо в `uint32`; путь с переполнением недостижим при этом условии.
- **Решение:** не подтверждено, ложное срабатывание для текущей реализации; защитную проверку сохранить.
- **Проверки:** добавлен `TestVerifyPasswordRejectsWrongDecodedHashLength` для 31 и 33 байт; существующий `TestHashPasswordUsesUniqueArgon2idSalt` проверяет допустимый 32-байтовый verifier, правильный и неправильный пароль. Проверки прошли.
- **Связь:** T-10 → SR-10 → D-04. Пересмотреть при изменении формата verifier, допустимой длины или ветвления перед Argon2id.

### S09-02 - два G124: атрибуты сессионной cookie

- **Места:** [http.go](internal/auth/http.go), `setSessionCookie` и `clearSessionCookie`.
- **Сигнал:** возможное отсутствие безопасных `Secure`, `HttpOnly` или `SameSite`, MEDIUM / HIGH confidence.
- **Проверка причины:** в обоих местах явно заданы `HttpOnly=true`, `SameSite=Lax`, `Path=/`, отсутствует `Domain`. Значение `Secure` берётся из `CookieSecure()`: `NewService` устанавливает его при HTTPS-origin и выбирает имя `__Host-session`. Анализатор не выводит значение вызова метода в литерале cookie.
- **Решение:** дефект HTTPS-конфигурации не подтверждён. Для локального HTTP `Secure=false` намеренно; это не защита передачи по HTTP. Внешнее размещение требует HTTPS и корректного `TRUSTED_ORIGIN`; реальное TLS/proxy-развёртывание этим запуском не проверялось.
- **Проверки:** новый `TestSessionCookiePolicyFollowsConfiguredOrigin` создаёт настоящий `Service` для HTTPS и локального HTTP, затем проверяет выдачу и удаление cookie, имя, флаги, путь и удаление значения. `TestProductionSessionCookieAttributes` также прошёл.
- **Связь:** D-01 и SR-09. Пересмотреть при изменении определения безопасного origin, cookie policy или способа размещения.

### S09-03 - ESLint: чтение словаря подписей

- **Место:** [app.ts](web/src/app.ts), `statusBadge`, `labels[status]`.
- **Сигнал:** `security/detect-object-injection`.
- **Проверка причины:** операция только читает фиксированный словарь подписей. Статусы ограничены моделью и CHECK в БД; результат передаётся в `element`, использующий `textContent`. Нет записи в объект, вычисления кода или решения о полномочиях. Даже неожиданный ключ не превращает эту операцию в prototype pollution или HTML-инъекцию.
- **Решение:** ложное срабатывание широкого правила в этом месте. Сигнал оставлен в отчёте; правило продолжает работать.
- **Связь:** безопасный текстовый вывод D-02. Пересмотреть при появлении записи по динамическому ключу, HTML parsing или использования значения для управления доступом.

### S09-04 - поиск секретов

Оба первичных отчёта Gitleaks пусты (`[]`): секретов по штатному профилю не обнаружено. Детекторы могут пропустить низкоэнтропийные пароли и неизвестные форматы; недоступные/удалённые refs и внешние хранилища не входят в область проверки.

## Воспроизведение

Установите Go из `go.mod`, Node.js 24 и Git. Из официальных releases установите [gosec 2.30.0](https://github.com/securego/gosec/releases/tag/v2.30.0) и [Gitleaks 8.30.1](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1), сверив архивы с опубликованными checksums. Для сканирования истории требуется полный clone; shallow clone отклоняется.

```powershell
npm.cmd ci --ignore-scripts
npm.cmd run build
gosec -version
gitleaks version
npm.cmd run security:scan
```

Если бинарники не в PATH, укажите полные пути в `$env:GOSEC_BIN` и `$env:GITLEAKS_BIN`. Дополнительный аргумент задаёт каталог нового результата: `npm.cmd run security:scan -- reports/security/local/recheck`. Не перезаписывайте сохранённые `s09-before` и `s09-after` обычным повтором.

[Скрипт](scripts/security-scan.mjs) возвращает 0 после полного запуска без неразобранных сигналов и находок секретов, 1 при неразобранных SAST-сигналах или любых находках секретов, 2 при ошибке инструмента, версии, разбора или неполной истории. Для Gitleaks задан отдельный код находок `10`; скрипт также проверяет сообщения уровня error, поскольку ошибки Git могут сопровождаться кодом 0. Ошибки сканирования приводят к незавершённой проверке с итоговым кодом 2. Реестр [security-reviewed.json](security-reviewed.json) связывает решение с правилом, местом и SHA-256 всего соответствующего файла с нормализованными LF. Изменение файла требует повторного разбора; глобальных исключений правил нет. Значения секретов маскируются до сохранения отчёта Gitleaks; его консольный вывод не сохраняется.

В CI отдельная задача `security` использует полный checkout, закреплённые Linux-архивы с проверкой SHA-256 и публикует первичные результаты как artifact `security-<attempt>`. Проверка текущего дерева охватывает отслеживаемые и новые неигнорируемые проектные файлы.

Ограничения SAST: это набор синтаксических/типовых проверок, не полное доказательство корректности бизнес-авторизации или потоков данных. ESLint не является полноценным межфункциональным taint-анализом браузера; gosec в этом запуске не покрывает `_test.go`. SCA, SBOM, DAST и аудит контейнерных уязвимостей сюда не включены.
