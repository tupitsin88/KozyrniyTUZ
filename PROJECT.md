# Паспорт проекта

## Общие сведения

Название команды: KozyrniyTUZ  
Название продукта: Сервис клубного членства  
Коды участников: M1, M2, M3  
Статус ранней калибровки: черновик

## 1. Назначение

Сервис объединяет несколько клубов на одной платформе. Пользователь создаёт клуб или подаёт заявку в существующий клуб, видит свои клубы в профиле и читает их материалы. Создатель клуба становится его администратором, получает club-member для этого клуба и управляет заявками, участниками и материалами. Один суперпользователь удаляет клубы.

У пользователя есть только один тип тега: club-member. Тег относится к конкретному клубу. Если пользователь получил club-member для клуба «Кино», он видит все материалы «Кино», но не получает доступ к материалам других клубов. Одобренная заявка добавляет пользователю этот тег для выбранного клуба.

## 2. Граница продукта

В продукт входит:

- создание клубов пользователями;
- назначение создателя администратором созданного клуба и добавление ему club-member;
- удаление клубов суперпользователем;
- просмотр списка клубов;
- регистрация и вход;
- профиль пользователя со списком клубов, в которых у него есть тег club-member;
- подача заявки в конкретный клуб;
- просмотр статуса своей заявки;
- рассмотрение заявки администратором клуба;
- добавление и удаление тега club-member для конкретного клуба администратором клуба;
- создание, изменение и просмотр материалов клуба администратором клуба;
- проверка доступа к материалам по совпадению клуба материала и клуба тега;
- браузерный интерфейс для основных действий;
- хранение данных в PostgreSQL.

Удаление клуба доступно только суперпользователю. Оно прекращает доступ к его материалам и скрывает его из пользовательского списка. Заявки, материалы, теги и права администратора удалённого клуба остаются в базе в архивном состоянии и не участвуют в выдаче доступа.

Внешнее окружение и внешние системы:

- браузер пользователя;
- PostgreSQL;
- Go-сервер;
- TypeScript-клиент.

В продукт не входят:

- оплата членских взносов;
- интеграции с платёжными и университетскими системами;
- внешняя проверка личности;
- email, SMS и push-уведомления;
- чат, форум и социальная сеть;
- мобильное приложение;
- управление физическим доступом в помещения;
- другие типы пользовательских тегов;
- настройка ролей через интерфейс.

## 3. Пользователи, роли и доступные действия

Роли доступа:

- User: обычный пользователь;
- Administrator: администратор конкретного клуба;
- SuperUser: суперпользователь платформы.

Administrator связан с конкретным клубом. Создатель клуба получает эту роль и club-member для созданного клуба. SuperUser существует в одном экземпляре на всю платформу. Тег club-member не является ролью. Запись тега всегда содержит пользователя и клуб. Один пользователь может иметь этот тег в нескольких клубах.

| Пользователь | Условие | Разрешённые действия | Запрещённые действия |
| --- | --- | --- | --- |
| Пользователь | Роль User | Создавать клубы; подавать заявки; видеть профиль и свои заявки | Рассматривать чужие заявки; менять теги; просматривать материалы клуба без club-member |
| Член клуба | Роль User, есть club-member для клуба | Видеть клуб в профиле; читать все материалы этого клуба | Рассматривать заявки; менять теги; читать материалы другого клуба без отдельного club-member |
| Администратор клуба | Роль Administrator для конкретного клуба | Рассматривать заявки этого клуба; добавлять и удалять club-member этого клуба; создавать и изменять его материалы | Управлять заявками, тегами или материалами другого клуба; удалять клуб |
| Суперпользователь | Роль SuperUser | Удалять любой клуб | Просматривать и рассматривать заявки; менять теги; создавать или изменять материалы; получать доступ к материалам клуба только из-за роли SuperUser |

## 4. Сквозные сценарии

### Сценарий 1. Подать заявку в клуб

- Участник: кандидат.
- Начальное условие: пользователь вошёл в систему, клуб активен, у пользователя нет club-member для этого клуба и нет ожидающей заявки в него.
- Действия: пользователь выбирает клуб, заполняет форму и отправляет заявку.
- Результат: создаётся заявка со статусом pending; она отображается в профиле пользователя.
- Изменение состояния: сохраняются идентификаторы пользователя и клуба, текст заявки, статус и время создания.

### Сценарий 2. Рассмотреть заявку

- Участник: администратор клуба.
- Начальное условие: существует заявка со статусом pending, клуб активен, а администратор управляет этим клубом.
- Действия: администратор открывает заявку и выбирает approved или rejected.
- Результат при approved: заявка получает статус approved; пользователю добавляется club-member для клуба из заявки.
- Результат при rejected: заявка получает статус rejected; тег не добавляется.
- Изменение состояния: сохраняются статус заявки, идентификатор администратора и время решения; при approved появляется запись тега пользователя для клуба.

### Сценарий 3. Работать с несколькими клубами

- Участник: пользователь.
- Начальное условие: пользователь вошёл в систему и состоит хотя бы в одном клубе.
- Действия: пользователь открывает профиль, видит список клубов с club-member, выбирает один из них и открывает его материалы.
- Результат доступа: сервер возвращает все материалы выбранного клуба, если у пользователя есть club-member для этого клуба.
- Результат отказа: сервер не возвращает материалы, если клуб удалён или у пользователя нет club-member для него.
- Изменение состояния: данные не изменяются; доступ проверяется для каждого запроса по паре пользователь - клуб.

## 5. Значимые данные и объекты

| Данные или объект | Для кого важны | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Клуб | Пользователи, администратор клуба, суперпользователь | Раскрывает название и описание клуба | Пользователь не сможет найти клуб; удалённый клуб может остаться доступным |
| Право администратора клуба | Администратор клуба | Раскрывает, кто управляет клубом | Посторонний сможет модерировать клуб или действующий администратор потеряет управление |
| Заявка | Кандидат, администратор клуба | Раскрывает содержание заявки | Заявка может попасть не в тот клуб, быть рассмотрена неверно или потеряна |
| Тег club-member для пары пользователь - клуб | Пользователь, администратор клуба | Раскрывает участие пользователя в конкретном клубе | Пользователь получит доступ к чужому клубу или потеряет доступ к своему |
| Материал клуба | Члены клуба, администратор клуба | Закрытое содержимое станет доступно постороннему | Участник прочитает неверный материал, не получит нужный материал или увидит материал другого клуба |

## 6. Компоненты и внешние взаимодействия

- TypeScript-клиент показывает список клубов, профиль, заявки, материалы и страницы управления клубом.
- Go API проверяет право администратора в конкретном клубе, право SuperUser на удаление клуба и наличие club-member для выбранного клуба.
- PostgreSQL хранит пользователей, глобальные роли, права администратора клубов, клубы, заявки, теги пользователей и материалы.
- API передаёт клиенту только материалы того клуба, для которого у пользователя есть club-member.
- Административные изменения клубов, заявок, тегов и материалов сохраняются в PostgreSQL.

## 8. Минимальное функциональное ядро

Обязательные функции:

- создание клуба пользователем с выдачей ему права Administrator и club-member для этого клуба;
- удаление клуба суперпользователем;
- регистрация и вход;
- роли User, Administrator и SuperUser;
- профиль со списком клубов пользователя;
- подача одной pending-заявки в каждый выбранный клуб;
- одобрение или отклонение pending-заявки администратором клуба;
- добавление club-member только для клуба одобренной заявки;
- удаление club-member для конкретного клуба администратором этого клуба;
- создание и просмотр материалов клуба администратором этого клуба;
- выдача всех материалов клуба только пользователю с club-member для этого клуба;
- сохранение пользователей, клубов, заявок, тегов и материалов в PostgreSQL;
- web-интерфейс для этих действий.

Функции, которые можно исключить при нехватке времени:

- изменение или отзыв pending-заявки;
- поиск, категории и сортировка клубов и материалов;
- загрузка файлов; на первом этапе материалы содержат текст;
- передача права администратора другому пользователю;
- история изменений клубов и материалов;
- восстановление удалённого клуба через интерфейс;
- отдельная мобильная версия.

## 9. Стек и путь к первой работающей версии

Основные технологии:

- backend: Go;
- frontend: TypeScript;
- хранилище: PostgreSQL;
- взаимодействие клиента и сервера: HTTP и JSON.

Внешние сервисы для запуска не нужны. Сервер, клиент и PostgreSQL запускаются локально.

Первый результат:

1. Go API подключается к PostgreSQL.
2. В базе есть пользователи, клубы и теги club-member, связанные с конкретным клубом.
3. Пользователь создаёт клуб, становится его администратором и получает club-member.
4. Пользователь открывает профиль и видит, в каких клубах он состоит.
