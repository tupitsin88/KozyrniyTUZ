# Паспорт проекта

## Общие сведения

Название команды: KozyrniyTUZ  
Название продукта: Сервис клубного членства  
Коды участников: M1, M2, M3, M4

Статус ранней калибровки: согласовано

## 1. Назначение

Сервис объединяет несколько клубов на одной платформе. Аккаунт с глобальной ролью User создаёт клуб или подаёт заявку в существующий клуб, видит свои клубы в профиле и читает их материалы. Создатель клуба получает дополнительное полномочие Administrator и club-member для этого клуба и управляет заявками, участниками и материалами. Один SuperUser удаляет клубы.

У пользователя есть только один тип тега: club-member. Тег относится к конкретному клубу. Если пользователь получил club-member для клуба «Кино», он видит все материалы «Кино», но не получает доступ к материалам других клубов. Одобренная заявка добавляет пользователю этот тег для выбранного клуба.

## 2. Граница продукта

В продукт входит:

- создание клубов аккаунтами с глобальной ролью User;
- назначение создателя администратором созданного клуба и добавление ему club-member;
- удаление клубов суперпользователем;
- просмотр списка клубов;
- регистрация и вход по паролю;
- профиль пользователя со списком клубов, в которых у него есть тег club-member;
- подача заявки в конкретный клуб аккаунтом с глобальной ролью User;
- просмотр статуса своей заявки;
- рассмотрение заявки администратором клуба;
- добавление и удаление тега club-member для конкретного клуба администратором клуба;
- создание, изменение и просмотр материалов клуба администратором клуба;
- проверка доступа к материалам по совпадению клуба материала и клуба тега;
- браузерный интерфейс для основных действий;
- хранение данных в PostgreSQL.

Удаление клуба доступно только суперпользователю. Оно прекращает доступ к его материалам и скрывает его из пользовательского списка. Заявки, материалы, теги и права администратора удалённого клуба остаются в базе в архивном состоянии и не участвуют в выдаче доступа.

Граница ответственности команды:

- TypeScript-клиент, Go API и PostgreSQL — компоненты продукта, которые проектирует и развёртывает команда;
- браузер пользователя — внешняя клиентская среда, из которой в API поступают недоверенные данные;
- хостовая операционная система, среда развёртывания и оператор инфраструктуры находятся вне интерфейсов продукта. Прямой доступ к серверу и управление PostgreSQL не предоставляются пользователям через приложение.

В продукт не входят:

- оплата членских взносов;
- интеграции с платёжными и университетскими системами;
- внешняя проверка личности;
- email, SMS и push-уведомления;
- чат, форум и социальная сеть;
- мобильное приложение;
- управление физическим доступом в помещения;
- другие типы пользовательских тегов;
- HTML, Markdown и другой rich text; пользовательские строки отображаются как обычный текст;
- настройка ролей через интерфейс;
- встроенные механизмы подачи жалоб на контент и автоматическая модерация текста материалов; при их появлении команда отдельно пересматривает границы, SR, T и D;
- сброс и восстановление паролей через интерфейс (включая аккаунт SuperUser).

## 3. Пользователи, роли и доступные действия

Глобальные роли взаимоисключающи:

- User: обычный пользователь;
- SuperUser: суперпользователь платформы.

Administrator — не отдельная глобальная роль, а дополнительное полномочие User в конкретном клубе. Получив его, User сохраняет базовые возможности: может создать ещё один клуб или подать заявку в другой. Создатель клуба получает Administrator и club-member созданного клуба. Тег club-member также не является ролью: запись всегда содержит пользователя и клуб, а один пользователь может иметь этот тег в нескольких клубах.

В системе ровно один SuperUser: он не получает Administrator и не может создавать клубы или новые заявки. До приёма HTTP-запросов сервер проверяет число таких записей. Если записей нет, bootstrap требует обе переменные окружения `BOOTSTRAP_SUPERUSER_LOGIN` и `BOOTSTRAP_SUPERUSER_PASSWORD`; без любой из них API не запускается. При наличии обеих сервер в транзакции создаёт единственного SuperUser и его Argon2id-verifier по D-04. Если запись уже ровно одна, bootstrap не меняет её независимо от наличия переменных; если записей больше одной, API не запускается. Значения переменных не попадают в журналы, ответы или базу в открытом виде.

Обычная публичная регистрация создаёт только User. Её строгая схема принимает только логин и пароль; любое дополнительное поле, в том числе `global_role`, `role_id` или `is_superuser`, отклоняется без создания учётной записи. В интерфейсе и публичном API нет функций создания, назначения, передачи, сброса или иной смены глобальной роли.

| Пользователь | Условие | Разрешённые действия | Запрещённые действия |
| --- | --- | --- | --- |
| Пользователь | Глобальная роль User | Создавать клубы; подавать заявки; видеть профиль и свои заявки | Рассматривать чужие заявки; менять теги; просматривать материалы клуба без club-member |
| Член клуба | Глобальная роль User, есть club-member для клуба | Все базовые действия User; видеть клуб в профиле; читать все материалы этого клуба | Рассматривать заявки; менять теги; читать материалы другого клуба без отдельного club-member |
| Администратор клуба | Глобальная роль User и Administrator конкретного клуба | Все базовые действия User; рассматривать заявки этого клуба; добавлять и удалять club-member этого клуба; создавать и изменять его материалы | Управлять заявками, тегами или материалами другого клуба; удалять клуб |
| Суперпользователь | Глобальная роль SuperUser | Удалять любой клуб; видеть собственные ранее созданные заявки и материалы при наличии club-member | Создавать клубы и новые заявки; просматривать чужие или рассматривать любые заявки; менять теги; создавать или изменять материалы; получать доступ к материалам клуба только из-за роли SuperUser |

## 4. Сквозные сценарии

### Сценарий 1. Подать заявку в клуб

- Участник: кандидат с глобальной ролью User, в том числе Administrator другого клуба.
- Начальное условие: пользователь вошёл в систему, клуб активен, у пользователя нет club-member для этого клуба и нет ожидающей заявки в него.
- Действия: пользователь выбирает клуб, заполняет форму и отправляет заявку.
- Результат: создаётся заявка со статусом pending; она отображается в профиле пользователя.
- Изменение состояния: сохраняются идентификаторы пользователя и клуба, текст заявки, статус и время создания.

### Сценарий 2. Рассмотреть заявку

- Участник: администратор клуба.
- Начальное условие: существует заявка со статусом pending, клуб активен, а администратор управляет этим клубом.
- Действия: администратор открывает заявку и выбирает approved или rejected.
- Результат при approved: заявка получает статус approved; пользователю добавляется club-member для клуба из заявки.
- Результат при rejected: заявка получает статус rejected; тег не добавляется.
- Изменение состояния: сохраняются статус заявки, идентификатор администратора и время решения; при approved появляется запись тега пользователя для клуба.

### Сценарий 3. Работать с несколькими клубами

- Участник: пользователь.
- Начальное условие: пользователь вошёл в систему и состоит хотя бы в одном клубе.
- Действия: пользователь открывает профиль, видит список клубов с club-member, выбирает один из них и открывает его материалы.
- Результат доступа: сервер возвращает все материалы выбранного клуба, если у пользователя есть club-member для этого клуба.
- Результат отказа: сервер не возвращает материалы, если клуб удалён или у пользователя нет club-member для него.
- Изменение состояния: данные не изменяются; доступ проверяется для каждого запроса по паре пользователь - клуб.

## 5. Значимые данные и объекты

| Данные или объект | Для кого важны | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Учётная запись и проверочный результат пароля | Все пользователи | Слабое хранение может позволить восстановить пароль и захватить аккаунт | Пользователь не сможет войти либо посторонний получит его полномочия |
| Серверная сессия | Вошедшие пользователи | Исходный токен позволяет действовать от имени владельца до отзыва или истечения | Пользователь потеряет вход либо запрос получит неверного субъекта и полномочия |
| Клуб и его состояние | Пользователи, администратор клуба, суперпользователь | ID, название и описание активного клуба публичны; их раскрытие само по себе не является нарушением | Несанкционированное изменение или архивирование лишит пользователей доступа к клубу; ошибочное сохранение доступа к архивному клубу нарушит правила доступа |
| Право администратора клуба | Администратор клуба | Раскрывает, кто управляет клубом | Посторонний сможет модерировать клуб или действующий администратор потеряет управление |
| Заявка | Кандидат, администратор клуба | Раскрывает содержание заявки | Заявка может попасть не в тот клуб, быть рассмотрена неверно или потеряна |
| Тег club-member для пары пользователь - клуб | Пользователь, администратор клуба | Раскрывает участие пользователя в конкретном клубе | Пользователь получит доступ к чужому клубу или потеряет доступ к своему |
| Материал клуба | Члены клуба, администратор клуба | Закрытое содержимое станет доступно постороннему | Участник прочитает неверный материал, не получит нужный материал или увидит материал другого клуба |

## 6. Компоненты и внешние взаимодействия

- TypeScript-клиент показывает список клубов, профиль, заявки, материалы и страницы управления клубом.
- Go API проверяет право администратора в конкретном клубе, право SuperUser на удаление клуба и наличие club-member для выбранного клуба.
- PostgreSQL хранит пользователей, проверочные результаты паролей, серверные сессии, глобальные роли, права администратора клубов, клубы, заявки, теги пользователей и материалы.
- API передаёт клиенту только материалы того клуба, для которого у пользователя есть club-member.
- Административные изменения клубов, заявок, тегов и материалов сохраняются в PostgreSQL.

## 8. Планируемое минимальное функциональное ядро продукта

Обязательные функции:

- создание клуба User с выдачей ему полномочия Administrator и club-member для этого клуба;
- удаление клуба суперпользователем;
- регистрация и вход по паролю;
- глобальные роли User и SuperUser и дополнительное клубное полномочие Administrator;
- профиль со списком клубов пользователя;
- подача одной pending-заявки в каждый выбранный клуб;
- одобрение или отклонение pending-заявки администратором клуба;
- добавление club-member только для клуба одобренной заявки;
- удаление club-member для конкретного клуба администратором этого клуба;
- создание, изменение и просмотр материалов клуба администратором этого клуба;
- выдача всех материалов клуба только пользователю с club-member для этого клуба;
- сохранение пользователей, проверочных результатов паролей, серверных сессий, ролей, прав Administrator, клубов, заявок, тегов и материалов в PostgreSQL;
- web-интерфейс для этих действий.

Функции, которые можно исключить при нехватке времени:

- изменение или отзыв pending-заявки;
- поиск, категории и сортировка клубов и материалов;
- загрузка файлов; на первом этапе материалы содержат текст;
- передача права администратора другому пользователю;
- история изменений клубов и материалов;
- восстановление удалённого клуба через интерфейс;
- отдельная мобильная версия.

## 9. Стек и минимальная запускаемая основа

Основные технологии:

- backend: Go;
- frontend: TypeScript;
- хранилище: PostgreSQL;
- взаимодействие клиента и сервера: HTTP и JSON.

Внешние сервисы для текущей минимальной основы не нужны. Полный сервер, клиент и PostgreSQL по плану будут запускаться локально.

Текущая минимальная запускаемая основа для EK1:

1. исходный код Go API находится в `cmd/server`;
2. сервер запускается локально без внешних зависимостей;
3. `GET /healthz` возвращает JSON со статусом `ok` и именем сервиса;
4. endpoint не реализует пользователей, PostgreSQL, аутентификацию или сценарии клубов: это сознательно оставлено следующей функциональной итерации.

Следующая функциональная итерация: Go API подключается к PostgreSQL; в базе появляются пользователи, клубы и теги `club-member`; User создаёт клуб, получает Administrator и открывает профиль.

## 10. Локальный запуск

Требуется Go `1.26` или совместимая версия. PostgreSQL, TypeScript-клиент и сторонние сервисы для этого health endpoint не требуются.

1. В корне репозитория запустите проверку:

   ```powershell
   go test ./...
   ```

   Ожидаемый результат: пакет `cmd/server` проходит два теста health endpoint.

2. Запустите API:

   ```powershell
   go run ./cmd/server
   ```

   Ожидаемый результат: в консоли появляется сообщение о прослушивании `:8080`.

3. В другом окне выполните:

   ```powershell
   curl.exe http://localhost:8080/healthz
   ```

   Ожидаемый результат: HTTP `200` и JSON с полями `"status":"ok"` и `"service":"club-membership"`. Для остановки сервера используйте `Ctrl+C` в окне запуска.
