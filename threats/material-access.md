# S03. Угрозы доступа к материалам и жизненного цикла клуба

Эта часть модели относится к чтению материалов и архивированию клуба. Она подготовлена по [паспорту проекта](../PROJECT.md) и [требованиям безопасности](../SECURITY_REQUIREMENTS.md). Go API и PostgreSQL описаны как **планируемые компоненты**: наличие работающей реализации здесь не утверждается. Общую архитектуру, остальные угрозы и окончательный приоритетный набор команда согласует в общей модели S03.

## Рассматриваемый участок системы

| Элемент | Значение для анализа |
| --- | --- |
| Субъекты | Пользователь без членства, участник клуба, администратор клуба, SuperUser. Роль SuperUser сама по себе не даёт права читать материалы. |
| Значимые объекты | Содержимое материала; связь материала с клубом; тег `club-member` для пары пользователь — клуб; состояние клуба «активен/архивирован». Название и описание активного клуба публичны и не рассматриваются как закрытые данные. |
| Поток чтения | Браузер передаёт Go API запрос списка материалов клуба или отдельного материала по идентификатору. API обращается к PostgreSQL за материалом, клубом и членством, затем возвращает материал либо отказ. |
| Поток удаления | SuperUser отправляет запрос на удаление клуба. API меняет состояние клуба на архивное; связанные материалы, теги и права сохраняются, но не должны продолжать давать доступ. |
| Граница доверия | Между браузером и API: идентификаторы материала и клуба и заявленная клиентом роль не доказывают право доступа. Сервер должен определять действующего пользователя независимо от этих полей. |

**Допущения:** пользователь может сформировать прямой запрос в обход интерфейса; идентификатор чужого материала может стать ему известен. Архивирование сохраняет записи, как указано в паспорте. Способ аутентификации и точные HTTP-маршруты пока не определены; сценарии не зависят от конкретного URL. Угрозы ниже описывают возможные нарушения, а не утверждают, что дефекты уже есть в коде.

## T-MAT-01 — Чтение материала другого клуба по идентификатору

- **Сценарий:** пользователь состоит в клубе «Кино», но не состоит в клубе «Музыка». Он отправляет прямой запрос материала «Музыки» по его идентификатору. Если API проверит только факт входа или наличие `club-member` *для какого-либо* клуба, материал будет возвращён постороннему.
- **Затронутый поток и граница:** недоверенный запрос браузер → API; далее чтение материала, его клуба и членства из PostgreSQL.
- **Недопустимое последствие:** раскрытие закрытого содержимого активного клуба человеку без членства в нём. Тот же сценарий применим к SuperUser без соответствующего `club-member`: глобальная роль не должна открывать материалы.
- **Связь:** [SR-01](../SECURITY_REQUIREMENTS.md) — членство должно относиться именно к клубу запрошенного материала, включая прямой запрос по ID.
- **Предварительный приоритет:** высокий. Клиент может менять переданный идентификатор; при ошибке привязки полномочия к клубу раскрывается закрытый материал. Для осуществления не требуется право администратора.

## T-MAT-02 — Старый тег открывает материал архивированного клуба

- **Сценарий:** SuperUser архивирует клуб «Кино». У бывшего участника остаётся запись `club-member` для этого клуба. Он отправляет прямой запрос старого материала. Если API проверит только сохранённый тег и не учтёт архивное состояние клуба, материал будет возвращён.
- **Затронутый поток и граница:** запрос браузер → API; API читает из PostgreSQL материал, тег и состояние клуба. Ошибка возникает при использовании неполного состояния для решения о доступе.
- **Недопустимое последствие:** после удаления клуба его закрытое содержимое остаётся доступным по прямому запросу вопреки прекращению доступа.
- **Связь:** [SR-01 и SR-03](../SECURITY_REQUIREMENTS.md) — материал архивного клуба недоступен даже при сохранившемся теге.
- **Предварительный приоритет:** высокий. Сохранение тегов после архивирования прямо предусмотрено продуктом; без учёта состояния клуба прежнее право выглядит действующим. Сценарий требует предварительного архивирования, что следует учесть при общем сравнении приоритетов.

## T-MAT-03 — Неуполномоченный пользователь архивирует клуб

- **Сценарий:** администратор клуба или обычный пользователь отправляет прямой запрос на удаление клуба. Если API принимает право администратора клуба или сам факт входа за полномочие SuperUser, клуб ошибочно переходит в архивное состояние.
- **Затронутый поток и граница:** недоверенный запрос браузер → API с идентификатором клуба; изменение состояния клуба в PostgreSQL.
- **Недопустимое последствие:** клуб исчезает из доступного списка, а его участники теряют доступ к материалам и функциям клуба без решения SuperUser.
- **Связь:** [SR-03](../SECURITY_REQUIREMENTS.md) — удалять активный клуб вправе только SuperUser; отказ не должен менять данные.
- **Предварительный приоритет:** высокий. Один успешный запрос затрагивает весь клуб и его участников. Реалистичность зависит от того, будет ли операция удаления доступна через API; она предусмотрена паспортом и поэтому рассматривается.

## Согласование с общей моделью S03

- **M2:** сверить названия компонентов, потоки и границу доверия с общей архитектурой; сравнить эти предварительные приоритеты с угрозами заявок и изменения членства. Не закреплять все три угрозы в приоритетном наборе автоматически.
- **M3:** после появления API проверить, совпадают ли предполагаемые потоки и условия атак с фактическими маршрутами и способом установления личности; при расхождении обновить модель.
- **M4:** проверить отдельно прекращение *управления* архивным клубом. Здесь подробно рассмотрено прекращение *чтения* материалов; это не покрывает все функции администратора из SR-03.

Для этих угроз пока не выбирается проектное решение `D-*` и не заявляется выполненная проверка: это работа S04 и следующих этапов.
