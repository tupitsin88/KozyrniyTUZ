# Модель угроз: создание клуба и заявки

## Назначение и граница анализа

Этот документ дополняет [паспорт проекта](PROJECT.md) и [требования безопасности](SECURITY_REQUIREMENTS.md). Он охватывает только операции создания клуба и создания заявки, то есть `SR-07` и `SR-08`. Угрозы доступа к уже созданным материалам, заявкам и управления членством остаются в зоне соответствующих требований `SR-01`–`SR-06`.

Идентификаторы `T-01`–`T-06` являются устойчивыми идентификаторами угроз этого набора. При объединении с работой команды их следует сверить с единым реестром `T-*`, не меняя смысл карточек.

## Архитектурный вид и потоки

В модели используются только компоненты из паспорта: браузер с TypeScript-клиентом, Go API и PostgreSQL. TypeScript-клиент выполняется на стороне пользователя, поэтому не считается доверенной стороной для API.

```text
Вошедший пользователь в браузере
        │
        │  создание клуба: название, описание;
        │  попытки передать userId получателя права/тега
        ▼
TypeScript-клиент  ───────────────►  Go API: создание клуба
                                      │ принимает решение, кому и для какого
                                      │ клуба выдать Administrator и club-member
                                      ▼
                                   PostgreSQL
                              клуб; право администратора;
                              тег club-member

Вошедший пользователь в браузере
        │
        │  создание заявки: clubId, текст;
        │  попытки передать ownerId или status
        ▼
TypeScript-клиент  ───────────────►  Go API: создание заявки
                                      │ принимает решение о владельце,
                                      │ статусе pending и активности клуба
                                      ▼
                                   PostgreSQL
                              заявка: владелец, клуб, текст,
                              статус, время создания
```

Ответы API возвращаются обратно в браузер: результат создания клуба или созданную заявку. Существенные изменения состояния происходят в PostgreSQL: создаётся клуб с двумя связанными записями доступа либо создаётся заявка.

### Граница доверия и недоверенный ввод

Главная граница доверия проходит между браузером (включая TypeScript-клиент) и Go API. Клиент может отправить прямой HTTP-запрос, изменить скрытое поле или вызвать недоступную в интерфейсе операцию. Поэтому сервер не может считать допустимыми только потому, что форма их не показывает:

- при создании клуба — название, описание, любой переданный идентификатор пользователя или клуба;
- при создании заявки — `clubId`, текст, любой переданный `ownerId` и `status`.

Для этих сценариев идентификатор текущего пользователя должен браться сервером из установленного контекста входа, а не из тела запроса. Способ аутентификации в этой модели не проектируется; анализируется решение Go API о допустимости операции.

Значимые свойства в данном срезе: корректная связь права Administrator и тега `club-member` с парой «текущий пользователь — новый клуб»; целостность владельца и начального статуса заявки; запрет создавать заявку в архивном клубе. Эти свойства важны потому, что определяют, кто сможет управлять клубом или чья заявка будет рассмотрена.

## Угрозы

### T-01 — В запросе создания клуба подменён получатель права и тега

**Сценарий.** Вошедший пользователь напрямую вызывает операцию создания клуба и передаёт идентификатор другого пользователя как получателя права Administrator и/или тега `club-member`. Go API использует это значение вместо идентификатора текущего пользователя, и другой пользователь получает право управления и членство в новом клубе.

- **Элемент модели:** поток «создание клуба» через границу браузер → Go API; операция создания клуба; хранилище прав и тегов.
- **Затронутый объект:** право Administrator и тег `club-member` нового клуба.
- **Нарушаемое свойство:** авторизация и целостность связи «пользователь — клуб».
- **Последствие:** посторонний получает возможность рассматривать заявки, менять участников и материалы нового клуба; создатель может остаться без ожидаемых прав.
- **Связанные требования:** `SR-07`.
- **Статус:** релевантна.
- **Приоритет:** высокий. Для сценария достаточно вошедшего пользователя и прямого запроса; нарушение сразу выдаёт полномочие администратора, которое нельзя передавать через обычный пользовательский сценарий.

### T-02 — Создатель привязывает выданные права к существующему клубу

**Сценарий.** Вошедший пользователь подставляет идентификатор существующего клуба в данные прямого запроса или изменяет его до обработки. API использует переданный идентификатор при выдаче Administrator либо `club-member`, а не идентификатор только что созданного клуба, и пользователь получает право или тег для чужого клуба.

- **Элемент модели:** поток «создание клуба»; операция создания клуба, которая создаёт клуб и связывает с ним право и тег; PostgreSQL.
- **Затронутый объект:** права администратора и теги существующего клуба.
- **Нарушаемое свойство:** авторизация и целостность границ между клубами.
- **Последствие:** создатель нового клуба получает полномочия управления в чужом клубе либо доступ к его материалам; состояние существующего клуба изменяется без разрешённого сценария.
- **Связанные требования:** `SR-07`; последствием также затрагивается доступ из `SR-01`.
- **Статус:** релевантна.
- **Приоритет:** высокий. Идентификатор клуба — недоверенный ввод, а успешная подмена даёт прямой доступ и административные полномочия в уже существующем клубе.

### T-03 — Частичное создание клуба оставляет несогласованные права создателя

**Сценарий.** Сбой API, базы данных или повторная обработка запроса происходит между сохранением нового клуба, права Administrator и тега `club-member`. В результате клуб создаётся, но у текущего пользователя отсутствует одно из обязательных назначений либо назначение связывается не с созданным клубом.

- **Элемент модели:** операция создания клуба; последовательные изменения в PostgreSQL: клуб, право администратора, тег.
- **Затронутый объект:** согласованное состояние нового клуба, права администратора и тега создателя.
- **Нарушаемое свойство:** целостность и доступность законных функций для создателя.
- **Последствие:** создатель не может управлять созданным клубом или читать его материалы; при ошибочной связи возможно изменение доступа к другому клубу.
- **Связанные требования:** `SR-07`.
- **Статус:** релевантна.
- **Приоритет:** средний. Для реализации нужен сбой или повторная обработка в момент изменения нескольких связанных записей, но последствия нарушают основной сценарий создания клуба и могут затронуть права доступа.

### T-04 — Заявка создаётся от имени другого пользователя

**Сценарий.** Вошедший пользователь передаёт в запросе создания заявки `ownerId` другого пользователя. Go API сохраняет этот идентификатор вместо идентификатора текущего пользователя, и в активном клубе появляется заявка от имени жертвы.

- **Элемент модели:** поток «создание заявки» через границу браузер → Go API; операция создания заявки; хранилище заявок.
- **Затронутый объект:** владелец, текст и статус заявки.
- **Нарушаемое свойство:** подлинность автора и целостность данных заявки.
- **Последствие:** администратор рассматривает заявку как принадлежащую другому человеку; при дальнейшем одобрении `SR-04` членство может быть выдано не тому пользователю.
- **Связанные требования:** `SR-08`; возможное последствие связано с `SR-04`.
- **Статус:** релевантна.
- **Приоритет:** средний. Достаточно прямого запроса от любого вошедшего пользователя, а нарушение искажает данные основного сценария и способно привести к неверной выдаче членства, но само по себе ещё не даёт атакующему доступ к клубу.

### T-05 — Заявка создаётся с обходом статуса pending

**Сценарий.** Вошедший пользователь передаёт `status: approved` или `status: rejected` при создании заявки. API принимает значение, и в хранилище появляется заявка, которая не прошла обязательное начальное состояние `pending`.

- **Элемент модели:** поток «создание заявки»; решение Go API о начальном статусе; запись заявки в PostgreSQL.
- **Затронутый объект:** статус заявки и порядок её рассмотрения.
- **Нарушаемое свойство:** целостность жизненного цикла заявки.
- **Последствие:** создаётся ложная запись о решении либо заявка становится недоступной для штатного рассмотрения по `SR-04`, которое допускает только pending-заявки. Модель не предполагает, что один лишь статус `approved` автоматически выдаёт тег: такая выдача определена только при рассмотрении заявки администратором.
- **Связанные требования:** `SR-08`, `SR-04`.
- **Статус:** релевантна.
- **Приоритет:** средний. Атаке достаточно изменить тело запроса; она не предоставляет членство напрямую, но нарушает основной порядок принятия решения и целостность данных заявки.

### T-06 — Заявка создаётся в удалённом клубе

**Сценарий.** Вошедший пользователь отправляет идентификатор архивного клуба как `clubId`. API не проверяет активное состояние клуба, и в архиве появляется новая заявка.

- **Элемент модели:** поток «создание заявки»; проверка состояния клуба в Go API; клуб и заявка в PostgreSQL.
- **Затронутый объект:** состояние удалённого клуба и заявка, связанная с ним.
- **Нарушаемое свойство:** целостность жизненного цикла клуба и согласованность заявок.
- **Последствие:** в неактивном клубе появляются новые данные, которые не должны участвовать в работе сервиса; заявка не имеет штатного пути рассмотрения и может исказить состояние при последующем восстановлении или анализе архива.
- **Связанные требования:** `SR-08`, а состояние удалённого клуба задаёт `SR-03`.
- **Статус:** релевантна.
- **Приоритет:** средний. Прямой запрос легко сформировать, однако по заданной модели он не должен сразу раскрывать материалы или выдавать права; основной ущерб — нарушение согласованности и правил архива.

## Проверка полноты и приоритетов

Проверка STRIDE дала конкретные сценарии, а не обязательные шесть строк: подмена автора проявилась в `T-04`; несанкционированное изменение — в `T-01`, `T-02`, `T-03`, `T-05` и `T-06`; повышение привилегий — в `T-01` и `T-02`. Для отрицания действий отдельный сценарий не включён: в данной архитектуре не описан журнал значимых действий и нет требования к подотчётности. Раскрытие данных не является прямым результатом самих операций создания; оно анализируется в `SR-01` и `SR-02`.

Все значимые свойства данного среза покрыты: корректность получателя и клуба для выдаваемых прав — `T-01`–`T-03`; подлинность владельца, жизненный цикл заявки и состояние целевого клуба — `T-04`–`T-06`. Приоритетными для будущих проектных решений отмечены `T-01` и `T-02`: оба сценария дают несанкционированные полномочия или доступ к клубу. Остальные угрозы важны для корректности основных сценариев, но не дают прямого доступа без дополнительного нарушения.

## Оставшийся разрыв для команды

Паспорт в сценарии подачи заявки устанавливает условие «нет ожидающей заявки в этот клуб», но `SR-08` не закрепляет поведение при повторных или одновременно отправленных запросах. Массовое или параллельное создание нескольких pending-заявок может создать дубли и нагрузку на рассмотрение. Это не включено как `T-*` данного среза, потому что для него нет однозначного `SR-*`; при сохранении этого правила команде следует уточнить критерий `SR-08` отдельным требованием о единственности pending-заявки и затем оценить соответствующую угрозу.
